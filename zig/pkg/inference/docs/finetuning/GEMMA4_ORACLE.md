# Gemma 4 oracle and benchmark contracts

The Gemma 4 reference tooling compares Antfly training with pinned external
implementations without making an external framework part of the production
runtime. It is designed for reproducible correctness and performance evidence,
not ad hoc local measurements.

## Locked inputs

`scripts/gemma4_oracle.lock.json` binds:

- model and tokenizer identities
- dataset revisions and deterministic fixture generation
- Python, package, and framework source revisions
- target modules, rank/alpha, optimizer settings, and sequence lengths
- numerical tolerance profiles
- benchmark protocol and hardware requirements

`scripts/compare_gemma4_lora_hf_zig.py validate-lock` validates the lock and
its referenced requirements files without loading a model. Oracle and
benchmark runners operate offline after admission and fail if their source,
dependencies, or bound inputs drift.

## Artifact roles

The contract keeps these roles distinct:

- immutable input: model, tokenizer, dataset, lock, and prepared rows
- producer output: traces, adapters, benchmark samples, and build receipts
- comparison output: parity summaries and release decisions
- publication marker: a closed `COMPLETE.json` ledger

Evidence publication is no-replace. Validators reject symlinks, unexpected
files, incomplete ledgers, modified payloads, and output paths that overlap an
immutable input.

## Deterministic fixtures

The checked-in fixture specification is
`testdata/gemma4_oracle/contract_cases.json`. Generate and verify a fixture
with:

```sh
python3 scripts/generate_gemma4_oracle_fixture.py \
  --output fixture.jsonl --manifest fixture.manifest.json \
  --train-count 8 --eval-count 4 --test-count 4

python3 scripts/generate_gemma4_oracle_fixture.py \
  --output fixture.jsonl --manifest fixture.manifest.json \
  --train-count 8 --eval-count 4 --test-count 4 --check
```

The manifest binds the exact generated bytes and split membership.

## Correctness comparison

`scripts/export_gemma4_lora_hf_oracle.py` produces the pinned HF/PEFT trace.
`scripts/compare_gemma4_lora_hf_zig.py` validates and compares framework
artifacts. Comparisons cover:

- rendered tokens and causal labels
- initial logits and loss
- raw gradients and global gradient norm
- optimizer moments and parameter updates
- adapter tensor names, shapes, and values
- checkpoint/resume trajectory

Adapter keys are normalized only through explicit, versioned translations.
Unknown, missing, duplicated, or lossy mappings fail closed. Numerical checks
include maximum absolute error, relative L2 error, cosine similarity, and the
recomputed raw-gradient norm.

## MLX performance comparison

The same-host performance tools are:

- `scripts/build_and_attest_gemma4_mlx.py`
- `scripts/run_gemma4_lora_mlx_benchmark.py`
- `scripts/run_antfly_gemma4_lora_benchmark.py`
- `scripts/run_gemma4_lora_benchmark_campaign.py`
- `scripts/bench_gemma4_lora_mlx_zig.py`

Both runners consume the same prepared row and canonical F32 LoRA tensors,
synchronize the device at optimizer boundaries, and emit samples conforming to
`scripts/gemma4_mlx_benchmark.schema.json`. Samples bind the runner source,
native build receipt, workload, complete loss history, gradient evidence,
fallback counters, timing protocol, and peak memory.

Run release comparisons in alternating fresh processes on the same machine.
Diagnostic samples from a dirty source tree are marked non-release and cannot
satisfy the campaign gate.

## DPO and GRPO comparison

The preference comparison tools are:

- `scripts/materialize_gemma4_dpo_hf_parity.py`
- `scripts/run_gemma4_dpo_mlx_benchmark.py`
- `scripts/evaluate_gemma4_dpo_adapters_mlx.py`
- `scripts/run_gemma4_grpo_mlx_benchmark.py`
- `scripts/run_gemma4_cuda_preference_smoke.py`

The DPO materializer creates provenance-bound training and disjoint holdout
rows. Adapter evaluation uses one runtime for both outputs so framework
loading, tokenization, and scoring are held constant. The GRPO comparison binds
the ranked sampling contract, rewards, initial token IDs, reference parity,
loss trajectory, and optimizer updates.

The CUDA preference smoke admits BF16 Safetensors only, runs DPO and GRPO
through one shared model/backend session, and requires:

- strict CUDA execution with zero fallback and unexpected host gradients
- the expected number of optimizer updates
- finite objective and reward telemetry
- exact trainable-tensor movement
- a changed final adapter checksum
- an embedded report matching the external report

## Contract tests

Run the offline contract suite with:

```sh
python3 -m unittest discover -v -s scripts -p 'test_*gemma4*py'
```

Run the focused native gate with:

```sh
zig build test-gemma4-finetune -j1 \
  -Dmetal=true -Dcuda=false -Donnx=false -Dpjrt=false \
  -Doptimize=ReleaseSafe --summary all
```

Use `TERMITE_REQUIRE_METAL_TESTS=1` or `TERMITE_REQUIRE_CUDA_TESTS=1` on the
corresponding hardware to make device tests fail rather than skip.

## Release requirements

Synthetic and tiny-model tests validate contracts but do not replace real E2B
and E4B evidence. A release campaign must additionally prove:

- pinned real-model parity at the required optimizer steps
- exact or tolerance-bounded checkpoint/resume behavior
- PEFT export load/forward compatibility
- zero host fallback on the selected native backend
- bounded peak memory without paging
- repeated stable throughput on the target hardware
- task-level quality on held-out data

Raw evidence remains external to the repository. Commit schemas, lock files,
deterministic fixtures, and the code required to reproduce and validate it;
do not commit machine-local logs, model outputs, adapters, or temporary paths.
